# PORTION P-05a — data: move engagement_signals DDL into the migration

Goal: C2.0 defines fourteen tables. data/migrate.py creates eleven. The three
missing ones — meeting_minutes, engagement_signals, report_history — are
instead created ad hoc by the repositories that needed them, and
engagement_signals is created by data/actions.py, which does not own it.

This card moves the engagement_signals DDL to where C2.4 says the schema lives.
The table definition itself is CORRECT and must be copied verbatim — this is a
move, not a redesign.

Note for the record: a code comment in data/actions.py claims "the frozen C2.4
DDL does not create it". That reading is wrong. C2.4 describes the migration in
prose and does not enumerate tables; C2.0 is the authoritative table list and
names all three. There is no contract defect here and nothing under contracts/
may be edited.

Contract: 02-CONTRACTS-data.md (C2.0 table list; C2.4 migration)

Files allowed (R10 budget: 2 source files + their tests):
  SOURCE  data/migrate.py
  SOURCE  data/actions.py
  TESTS   tests/data/test_migrate.py

Context Pack: this card · the C2.0 table list and the C2.4 migration section of
  contracts/02-CONTRACTS-data.md · data/migrate.py and data/actions.py, both
  in Files allowed — the DDL to move is already written in the second and the
  style to follow is in the first. Do not open any other .py file.

Done when:
  - data/migrate.py creates engagement_signals with EXACTLY the columns,
    types, constraints and defaults currently declared in data/actions.py.
    Copy the statement; do not rewrite it. Follow migrate.py's existing
    formatting (one column per line, aligned) rather than actions.py's.
  - the column naming convention of the existing eleven tables is preserved:
    the foreign key is project_code TEXT NOT NULL REFERENCES project(code).
    C2.0 writes project_id as shorthand; every implemented table uses
    project_code, and this table already does.
  - the index on engagement_signals(project_code, owner) moves with it — C2.4
    names a signals index explicitly.
  - data/actions.py no longer contains any CREATE TABLE or CREATE INDEX for
    engagement_signals. Its _ensure_columns function keeps its other work
    (the action-table column additions) unchanged.
  - test_migrate asserts engagement_signals exists after migrate() on a fresh
    db, with its full column list read from PRAGMA table_info and compared to
    the C2.0 column names.
  - the full suite is green. The signals tests written in P-09a must pass
    UNCHANGED — if any of them only passed because actions.py created the
    table, that is the defect this card fixes and the test should now pass on
    the migration instead.

Forbidden: renaming the table or any column; changing a type, constraint or
  default while moving the statement; editing anything under contracts/;
  touching data/minutes.py or data/reports_history.py (P-05b owns those);
  removing anything from _ensure_columns other than the engagement_signals
  DDL and its index.

Stop and ask if: the CREATE TABLE in data/actions.py disagrees with the C2.0 column list for engagement_signals. Report the disagreement and stop — reconciling a contract and a schema is not this card's job.
