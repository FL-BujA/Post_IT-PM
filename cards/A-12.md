# PORTION A-12 — data: gate exit_criteria and notes

Goal: C2.2 specifies GateRepo.create as:

    create(project_id, name, planned_date=None, exit_criteria="", notes="")

The built create takes only planned_date. C4.1 defines a route that sends
both missing fields:

    POST /api/projects/{code}/gates
         body {"name", "planned_date"|null, "exit_criteria", "notes"}

and C4.2's GateView carries them back out. Neither column exists on the
gate table, so this card changes the schema as well as the repository.

The migration must stay idempotent on an existing database. data/actions.py
already solves this: a PRAGMA table_info check, then ALTER TABLE for any
column that is absent. Follow that pattern rather than inventing one.

Contract: 02-CONTRACTS-data.md (C2.0 gate table, C2.2 GateRepo, C2.4 migration)

Files allowed (R10 budget: 2 source files + their tests):
  SOURCE  data/gates.py
  SOURCE  data/migrate.py
  TESTS   tests/data/test_gates_cycles.py (extend; do not rewrite)

Context Pack: this card · the C2.2 GateRepo block and the C2.0 gate table line of
  contracts/02-CONTRACTS-data.md · data/gates.py and data/migrate.py, both
  in Files allowed · the _ensure_columns function in data/actions.py is the
  idempotent-ALTER pattern — its shape is described in this card, so you do
  not need to open that file.

Done when:
  - the gate table gains two columns: exit_criteria TEXT and notes TEXT,
    both nullable, declared in migrate.py's SCHEMA_SQL alongside the
    existing gate columns.
  - a fresh database created by migrate() has both columns (asserted from
    PRAGMA table_info).
  - an EXISTING database without them gains them: migrate() checks
    PRAGMA table_info and issues ALTER TABLE gate ADD COLUMN for each
    absent column. A test creates a db, drops the two columns by rebuilding
    the table without them, runs migrate() again, and asserts both return.
  - migrate() remains idempotent: running it three times on the same db
    succeeds and the column count is unchanged after the second run.
  - GateRepo.create gains exit_criteria: str = "" and notes: str = "" as
    keyword-only parameters after planned_date, stores both, and returns a
    GateRow carrying them.
  - GateRow gains the two fields, in the table's column order, with
    to_dict() updated to match — data/rows.py is NOT in Files allowed, so
    if GateRow must change, STOP and say so rather than editing it.
  - every existing gate test passes with its intent intact; existing calls
    that omit the two parameters still work.
  - core.sig.txt regenerated and `make gate` green.

Forbidden: making either column NOT NULL (existing rows have no value);
  dropping or recreating the gate table on an existing database — the
  ALTER path is the only migration; changing record_outcome, get or
  list_for; editing anything under contracts/.

Stop and ask if: GateRow must gain fields but data/rows.py is not in Files allowed — report this and stop rather than editing it. Also stop if the gate table already has either column.
